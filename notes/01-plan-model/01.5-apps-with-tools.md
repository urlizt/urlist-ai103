# Using Tools with Generative AI

> Generative AI models are powerful but limited to the knowledge inside their training data. Tools extend these models so they can interact with the real world.

## Why Tools Matter
- **Access real‑time information**  
  Fetch live data such as weather, stock prices, or API responses.

- **Take actions**  
  Send emails, create records, trigger workflows, or perform tasks on behalf of the user.

- **Ground responses in facts**  
  Retrieve authoritative information to reduce hallucinations and improve accuracy.

- **Extend functionality**  
  Connect AI to business systems, databases, and custom logic.

- **Build intelligent workflows**  
  Chain multiple operations so the model can coordinate multi‑step processes.


## Key Concepts in This Module
- Tools are **specified in prompts** and executed by the **client application**, not the model itself.
- The client manages tool configuration, effectively creating a **custom AI assistant** inside the app.
- Learning tool‑based prompting is the foundation for building **agentic AI solutions**, where instructions + tools + model are packaged into a named agent.
> 📎 **Foundry Tools are not** the same as prompt‑specified tools; they are Azure AI APIs.

# What Are Tools?

> By default, the model chooses when to use a tool (and which one), based on the prompt. You can configure tool selection rules and use the Instructions (system prompt) parameter to guide this choice.


### Common Tools used in the OpenAI Responses API
- **code_interpreter** — Runs Python code generated by the model.
- **web_search** — Retrieves current internet information.
- **file_search** — Searches user‑uploaded files in a vector index.
- **function** — Calls custom functions in your application.

### Specifying Tools
- Tools are defined in the `tools` list when calling `responses.create()`

```python
from openai import OpenAI

client = OpenAI(
    base_url={openai_endpoint},
    api_key={auth_key_or_token}
)

response = client.responses.create(
    model={model_deployment},
    instructions="You are a helpful AI assistant.",
    input="Find me some information about vintage computers.",
    # Specify available tools as a JSON list
    tools=[
        { 
            # A tool definition
            "type": "{tool_type}",
            "{tool-specific-setting}": "{value}",
                ...
        },
        { 
            # Another tool definition
            "type": "{another_tool_type}",
            "{tool-specific-setting}": "{value}",
                ...
        }
    ]
)
print(response.output_text)
```

# `code_interpreter` Tool


> The **code_interpreter** tool gives a generative AI model access to a **sandboxed Python runtime**, allowing it to write and execute Python code during a conversation. Moves the model from **explaining** code to **running** code.  

- **Dynamic Python execution**   The model generates and runs Python code on demand.

- **File handling**   Upload, process, and download files (CSV, JSON, images, etc.).

- **Data analysis**   Perform calculations, statistics, transformations, and visualizations.

- **Real‑time feedback**   The model sees execution results and can correct errors.

- **Complex problem solving**   Useful for math, physics, simulations, and algorithm prototyping.

| Use Case | Example |
| :--- | :--- |
| Data Analysis | Parse a CSV and generate summary statistics |
| Mathematics & Physics | Solve differential equations or simulate physical scenarios |
| File Format Conversion | Convert JSON ↔ CSV or other formats |
| Prototyping | Test algorithms and ideas before formal implementation |

```python
...
# Get response using the code_interpreter tool
response = client.responses.create(
    model={model_deployment},
    instructions="You are an AI assistant that provides information. Use the python tool to run code for math problems.",
    input="What is the square root of 16?",
    tools=[{"type": "code_interpreter",
            "container": {"type": "auto"}}]
)
print(response.output_text)
```

> **How it works** - Request (inc. tool) -> Model decides if code execution req. -> Gernerates code -> runs n sandbox -> incorporates output in response.

## Best Practices
- **Be Specific**: Clearly describe data formats and expected outputs
- **Provide Context**: Include relevant domain knowledge in your prompts
- **Validate Results**: Always review AI-generated code before using it in production
- **Monitor Costs**: Code execution increases token consumption
- **Leverage Pre-installed Libraries**: pandas, numpy, matplotlib, etc., are already available
- **Handle Errors**: The model can identify errors and attempt automatic fixes

## Limitations
- No external network access within the sandbox
- Some libraries may not be available; let the model know if a standard library fails
- Timeout limits apply to long-running operations
- Memory constraints exist – use streaming or chunking for large datasets

# Web Search Tool

> `web_search` is a tool that gives the AI model the ability to retrieve **live, up‑to‑date information** from the internet at runtime. Instead of relying only on its static training cut‑off, the model can issue search queries, scan multiple sources, and synthesise a response based on current, verifiable content. This is critical for any topic where information changes frequently – news, prices, product launches, regulations, or scientific updates.

## Core Capabilities
- **Real‑time retrieval** – accesses data that is newer than the model's training date
- **Source transparency** – answers are linked to actual web pages (though citations are omitted in this summary)
- **Autonomous decision‑making** – the model decides if search is needed, what queries to run, and which results to use
- **Multi‑turn grounding** – can refine searches based on prior conversation context
- **Fallback behaviour** – if search results are insufficient, the model can acknowledge gaps or ask clarifying questions

```python
# Get response using the web_search tool
response = client.responses.create(
    model={model_deployment},
    instructions="You are an AI assistant. Use web search when current information is required.",
    input="What are three major announcements from Microsoft Build this week?",
    tools=[{"type": "web_search"}]
)
```

## When to Use It (Key Use Cases)
| Category | Example |
| :--- | :--- |
| **Breaking news** | "What were the key announcements from today's Apple event?" |
| **Market intelligence** | "Compare current pricing for AWS vs. Azure compute instances." |
| **Regulatory tracking** | "Has the EU AI Act been updated this month?" |
| **Fact validation** | "Check whether that viral health claim is supported by official health agencies." |
| **Product/tech specs** | "What are the latest features in the newest PyTorch release?" |


## Best Practices for Reliable Results
- **Be time‑aware** – include phrases like *"as of this week"*, *"latest"*, or specific dates to reduce ambiguous results
- **Guide source quality** – if you need authoritative info, prompt for *"official government sites"* or *"peer‑reviewed publications"*
- **Request structured output** – ask for bullet‑point summaries, tables, or pros/cons lists to make revision easier
- **Use follow‑up questions** – if the first search isn't precise, refine with additional queries (the model can handle this)
- **Set expectations** – the model may need to search multiple times; allow for slightly longer response times


## Important Limitations to Remember
- **No paywalled or login‑protected content** – only publicly indexed pages are accessible
- **Variable source reliability** – the AI does not have built‑in fact‑checking; critical claims still need human verification
- **Non‑deterministic** – search results change over time, so the same prompt can yield different answers on different days
- **Regional differences** – search results may vary depending on geographic and network policies
- **Latency and cost** – web retrieval adds extra time and consumes additional tokens, so use it only when genuinely needed

# `file_search` Tool

## What It Is
- A tool that allows the AI to search and retrieve information from **your own uploaded documents**
- Transforms a general-purpose model into a **domain‑specific assistant** grounded in internal knowledge
- Uses semantic search to find relevant content by meaning, not just exact keywords

> `file_search` turns a generic AI into a **private, document‑aware assistant** that answers questions using your internal files. It works best with well‑structured, current documents and focused, specific questions. Critical outputs should still be validated by a human.

## Core Capabilities
- **Document‑grounded responses** – Answers are based on your files, not general training data
- **Semantic retrieval** – Finds relevant passages even when phrasing doesn't match exactly
- **Vector store support** – Search across one or more indexed document collections
- **Traceable outputs** – Matched results can be included for debugging and transparency
- **Multi‑file handling** – Supports common formats like PDFs, Word, Excel, text, and markdown


```python
...
# Create vector store and upload a file
vector_store = client.vector_stores.create(name="policy-docs")
client.vector_stores.files.upload_and_poll(
    vector_store_id=vector_store.id,
    file=open("expenses_policy.pdf", "rb")
)

# Get response using the file_search tool
response = client.responses.create(
    model=model_deployment,
    instructions="You are an AI assistant that provides information from HR policy documents.",
    input="What's the maximum amount I can claim for a taxi ride?",
    tools=[{
        "type": "file_search",
        "vector_store_ids": [vector_store.id]
    }],
    include=["file_search_call.results"]
)
print(response.output_text)
```

## Common Use Cases

| Scenario | Example Application |
| :--- | :--- |
| HR and policy Q&A | Answer employee questions from internal handbooks |
| Customer support | Retrieve troubleshooting steps from product manuals |
| Legal and compliance | Locate specific clauses across multiple contracts |
| Technical documentation | Summarise capabilities from API or developer guides |
| Internal knowledge bases | Provide consistent answers from company wikis |


## Best Practices for Reliable Results

- **Use clean, current documents** – Outdated or poorly formatted files reduce retrieval accuracy
- **Keep vector stores focused** – Separate by domain (e.g., HR, legal, finance) to avoid cross‑pollution
- **Ask specific questions** – Focused prompts yield more relevant matches than vague ones
- **Test with sample queries** – Validate that the right content is being retrieved before production use
- **Review the matched passages** – Use response includes to verify what the model actually saw

# `function` Tool (Function Calling)

> Enables the model to request execution of **developer‑defined functions** in your application
- The model **does not run your code** – it emits a structured call, your code executes the logic, and you return the result
- Connects the model to external systems: APIs, databases, internal services, and business workflows


## Core Capabilities

- **Structured tool calls** – Model returns typed, parameterised function requests
- **Application‑controlled execution** – Your infrastructure decides when and how functions run
- **Flexible integration** – Can call anything: from simple utilities to complex microservices
- **Multi‑turn orchestration** – Model can call multiple tools in sequence or in parallel
- **Grounding in live data** – Answers can incorporate current system state


## How It Works (Step‑by‑Step)

1. **Define tools** – Provide function schemas (name, description, parameters) in the `tools` array
2. **User sends a prompt** – Model analyses intent against available tools
3. **Model decides to call** – If a function is needed, it emits a `function_call` object
4. **Your app intercepts** – You receive the function name and argument values
5. **Your code executes** – Run your business logic (API call, DB query, calculation)
6. **You return output** – Send the result back as a `function_call_output` item
7. **Model finalises** – It incorporates the tool response into its final answer

```python
    function_tools = [
        {
            "type": "function",
            "name": "get_time",
            "description": "Get the current time"
        }
    ]
```

## Common Use Cases

| Use Case | Example Application |
| :--- | :--- |
| **System integration** | Pull live customer data from your CRM |
| **Task automation** | Create support tickets or send notifications |
| **Real‑time lookups** | Query inventory, pricing, or availability |
| **Math and logic** | Perform heavy calculations or transformations |
| **Workflow orchestration** | Chain multiple tools to complete a complex task |


## Limitations to Remember

- The model only **requests** execution – your application must handle the actual run
- Tool arguments can be unpredictable; validation and sanitisation are mandatory
- Increased latency due to external calls (API, DB, compute)
- Token usage increases because tool definitions and outputs consume tokens
- Critical actions (financial, legal) should still be reviewed or gated with approvals
